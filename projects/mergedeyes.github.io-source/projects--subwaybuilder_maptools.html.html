<h2 class="heading-element" dir="auto">Usage</h2>
<h3 class="heading-element" dir="auto">Generating a map</h3>
<p dir="auto">This is handled by <code>build.py</code>, a thin wrapper around depot's own <code>depot.maps.MapGen</code> class - see depot's own <a href="https://github.com/Subway-Builder-Modded/depot/tree/main/examples/maps">examples/maps</a> (<code>HEL.py</code>/<code>LAXM.py</code>) for further <code>MapGen</code> configuration options and depot's README for the full <code>MapGen</code> parameter/method reference.</p>
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="python build.py"><pre class="notranslate"><code>python build.py
</code></pre></div>
<h3 class="heading-element" dir="auto">Generating demand data</h3>
<p dir="auto">This is handled by <code>run_demand_pipeline.py</code>, wrapping two composable pipeline stages exposed by <code>generate_demand_qzm_local.py</code> behind a small <code>DemandGen</code> class (<code>demand_gen</code>, already constructed for <code>CITY_CODE</code> at the bottom of the file) - the same build.py/<code>MapGen</code>-style shape, just for demand instead of map geometry.</p>
<p dir="auto">Job hubs and residential hubs are consolidated independently and never merge into each other - <code>RES_SIZE_RATIO</code>/<code>JOB_SIZE_RATIO</code> in <code>.env</code> (see above) control each side's hub size/count on its own. If commuters end up spread across too many small, scattered job destinations to plan a profitable line around, lower <code>JOB_SIZE_RATIO</code> to fold jobs into fewer, bigger hubs without changing residential granularity at all.</p>
<h4 class="heading-element" dir="auto"><code>DemandGen</code> inputs</h4>
<markdown-accessiblity-table><table>
<thead>
<tr>
<th>Parameter</th>
<th align="center">Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>city</code></td>
<td align="center">str. 3-4 character city code. Must match <code>CITY_CODE</code> in <code>.env</code> - <code>DemandGen</code> raises immediately if it doesn't, since every function it wraps is already wired to <code>CITY_CODE</code>, not to whatever's passed in here.</td>
</tr>
<tr>
<td><code>bbox</code></td>
<td align="center">list of floats. Bounding box for the map <code>[min_lon, min_lat, max_lon, max_lat]</code>. Resolved automatically from <code>.env</code>/<code>bbox_utils.get_bbox()</code> - passed in here mainly to keep this class's shape consistent with <code>MapGen</code>.</td>
</tr>
<tr>
<td><code>autofill_special_demand</code></td>
<td align="center">bool. Default: <code>True</code>. Auto-estimates a capacity for "landmark"-tier special demand (universities, hospitals, stadiums, museums, zoos) instead of opening a browser tab per one and waiting - same as the high-volume "common" types already get. Set <code>False</code> to go back to the manual review-in-browser flow instead (capped at 15 tabs per run); you can still hand-edit the special-demand JSON afterward either way.</td>
</tr>
</tbody>
</table></markdown-accessiblity-table>
<h4 class="heading-element" dir="auto"><code>DemandGen</code> methods</h4>
<markdown-accessiblity-table><table>
<thead>
<tr>
<th>Class method</th>
<th align="center">Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>run_all</code></td>
<td align="center">Full pipeline: OSM parsing, green-space capture, optional Zensus calibration, airport hub snapping, and base OSRM routing (<code>build_base_demand()</code>); then cluster/consolidate and named special demand (<code>enrich_demand()</code>). This is what <code>python run_demand_pipeline.py</code> runs by default.</td>
</tr>
<tr>
<td><code>run_enrich_only</code></td>
<td align="center">Re-runs ONLY the enrichment stage (cluster/consolidate + named special demand) against the existing base checkpoint (<code>demand_data_base.json</code>) - skips the much slower OSM parsing / airport snapping / base OSRM routing steps. Use after tuning <code>RES_SIZE_RATIO</code>/<code>JOB_SIZE_RATIO</code> in <code>.env</code> or hand-editing special-demand data. See <code>rerun_enrichment.py</code> for a ready-to-run example.</td>
</tr>
</tbody>
</table></markdown-accessiblity-table>
<p dir="auto">Both methods also rebuild <code>config.json</code> afterward (via <code>config_utils.py</code>) from <code>CITY_NAME</code>/<code>MAP_DESCRIPTION</code>/<code>MAP_CREATOR</code> in <code>.env</code> plus the population summed fresh from <code>demand_data.json</code> - there's no separate config-generation step or script to run by hand. <code>run_all</code> must complete at least once for a given city before <code>run_enrich_only</code> has a base checkpoint to enrich.</p>

<h2 class="heading-element" dir="auto">Running the scripts</h2>
<h3 class="heading-element" dir="auto">Precautions</h3>
<ol dir="auto">
<li>Install <a href="https://github.com/Subway-Builder-Modded/depot">depot</a>.</li>
<li>Run "pip install -r requirements.txt"</li>
<li>Download a .osm.pbf file you want to use to extract the mapdata from <a href="https://download.geofabrik.de/index.html" rel="nofollow">Geofabrik</a>.</li>
<li>Get your commuters data in the INSPIRE-Grid format. <a href="https://mobilithek.info/offers/767359761906577408" rel="nofollow">Germany</a></li>
</ol>
<h3 class="heading-element" dir="auto">Running the scripts</h3>
<ol dir="auto" start="5">
<li>Get your initial map data with depot, running build.py (Check examples directory within depot (HEL.py/LAXM.py))</li>
<li>Set <code>CITY_NAME</code>/<code>MAP_DESCRIPTION</code>/<code>MAP_CREATOR</code> in <code>.env</code> (see <a href="#setting-up-env-file">Setting up .env file</a> above) - required before this next step, since it now also writes <code>config.json</code> for you. Prepare the data, running run_demand_pipeline.py</li>
<li>Set correct coordinates for airport points, opening Google Maps and entering the correct cords into ./raw_map_files/CITY_CODE/custom_hubs.json, running open_maps.py</li>
<li>Generate the demand data, running run_demand_pipeline.py again. <code>config.json</code> is regenerated automatically at the end of this run too, with the final population - no separate config step needed. Reference for the full <code>config.json</code> schema: <a href="https://www.subwaybuilder.com/docs/v1.0.0/api-reference/cities" rel="nofollow">official documentation</a>.</li>
<li>Run "ship.py none", to create the ZIP file. (none: No version change, major: Bumb major version, minor: Bump minor version, patch: Bump patch version inside config.json)</li>
<li>Import your ZIP into Railyard (locally) and test your map ingame.</li>
<li>(Optional) Make changes to the map, demand configuration, description, etc. Run build.py (only if you change the initial map/city), run_demand_pipeline.py, ship.py &lt;none/major/minor/patch&gt; again.
<ul dir="auto">
<li>If you only changed something in the enrichment stage - <code>RES_SIZE_RATIO</code>/<code>JOB_SIZE_RATIO</code> or <code>CITY_NAME</code>/<code>MAP_DESCRIPTION</code>/<code>MAP_CREATOR</code> in <code>.env</code>, or hand-edited a special-demand JSON file - you don't need the full run_demand_pipeline.py run again. Run <code>rerun_enrichment.py</code> instead (see <a href="#demandgen-methods"><code>DemandGen</code> methods</a> above), which skips the much slower OSM parsing / airport snapping / base OSRM routing steps and still regenerates <code>config.json</code>:
<div class="snippet-clipboard-content notranslate position-relative overflow-auto" data-snippet-clipboard-copy-content="python rerun_enrichment.py"><pre class="notranslate"><code>python rerun_enrichment.py
</code></pre></div>
</li>
</ul>
</li>
<li>Publish your map to Github manually, OR:</li>
<li>Edit the parameters of publish.py and automatically publish your map to your Github-Repo, also generating a update.json for the SubwayBuilderModded Registry for your map automatically.</li>
</ol>
