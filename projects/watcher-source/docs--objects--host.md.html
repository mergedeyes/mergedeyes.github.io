host

A host is a machine or device to monitor: a server, a switch, a website. It gets services directly or through host groups and service groups.

[[host]]
name = "web01"
address = "10.0.0.5"
services = ["http"]

web01 gets the service http, and its check runs against 10.0.0.5. Because the host has an address, Watcher also pings it to decide whether the host is UP or DOWN, see Host state.

Hosts are written with double brackets, [[host]], because each one is an entry in a list. Each host needs a unique name.

Fields

Field Default Description
name Required. Unique name of the host.
address the name IP address or DNS name. Available in commands as $host.address$.
groups Host groups the host belongs to. See hostgroup.
services Services the host gets. See service. A check can be listed as it is, without a [service.<name>]: a built-in one like http or tls, or one of yours.
servicegroups Service groups the host gets; it gets all their services. See servicegroup.
vars Values for the $name$ macros of the host's services, and the tables for for_each. Win over host group vars. Built-in checks don't read them, except through macros like $host.vars.port$.
host_check from the host groups; otherwise ping if address is set The service or check that decides whether the host is UP or DOWN. It runs for the host itself and isn't one of its services. false: no host check, the host is always UP. See Host state.
graph the host check The service whose graph is shown on the host page. If the host doesn't have that service, or its graphs are off (graphs = false), the page shows the host check's graph.
ssh from the host groups Login for checks over SSH: { user, secret, port }. See ssh.
proxmox from the host groups For a Proxmox VE server: the API login, { secret, fingerprint, port, verify, discover }. For a VM or container on one: { host, vmid }. See proxmox.
enabled true false: the host is not monitored.
node local The node at the host's site. The Nodes page lists the host under it. local means this Watcher itself, the same as no node. Not yet: the node doesn't run the host's checks; the hub still does.
service.<name> A host service: settings of one service on this host only. See Host services.

Examples

A host with services

[[host]]
name = "web01"
address = "10.0.0.5"
services = ["http", "ssh"]

A host in host groups

The host gets the services and settings of its groups.

[[host]]
name = "db01"
address = "10.0.2.21"
groups = ["linux", "databases"]

A host with a service group

[[host]]
name = "web01"
servicegroups = ["linux-basics"]

Different values on one host

The check http uses $url$. This host checks another URL:

[[host]]
name = "shop"
services = ["http"]
vars.url = "/health"

One service per disk

The service disk has for_each = "disks". The host gets disk_root and disk_data. See for_each.

[[host]]
name = "db01"
services = ["disk"]
vars.disks.root = { path = "/" }
vars.disks.data = { path = "/srv", warn = "10%" }

A host without a host check

[[host]]
name = "printer"
address = "10.0.9.40"
services = ["snmp_toner"]
host_check = false

Another graph on the host page

[service.load]
command = "check_load -w 5,4,3 -c 10,8,6"

[[host]]
name = "app01"
address = "10.0.0.7"
services = ["load"]
graph = "load"

The host page shows the graph of load instead of ping. graph only chooses what is shown: the host needs the service, here from services.

A host that is not monitored

[[host]]
name = "old01"
enabled = false

Hosts and services that are disabled or removed from the configuration keep their history in the database.

Host services

[host.service.<name>] below a host holds settings for one service on this host only. Write it after the host's other fields, because in TOML every key below a [host.service.x] line belongs to that service.

What it does depends on the service:

  • The host already has the service (from services, a host group or a service group): the settings change it on this host.
  • The host doesn't have the service, but [service.<name>] exists: the host gets the service, with these settings.
  • Neither: a new service that exists only on this host. Like a normal service, it uses the check with the same name unless check or command is set.

Fields

A host service takes the same fields as a service:

Field Default Description
check the service's check, or the check with the same name The check to use.
for_each the service's Name of a host var. Creates one service per entry of that var. See for_each.
groups More service groups for the service on this host. They add to the service's groups.
enabled true false: this host doesn't get the service.
title the service's or check's title Name shown in the web UI. Can contain macros.
command the service's or check's The command to run. Can contain macros.
builtin the service's or check's Use a check built into Watcher instead of a command: ping, tcp, http, dns, tls, or one of the Proxmox VE checks. See Built-in checks.
shell false true runs the command with /bin/sh -c, needed for pipes, $(...) or &&.
run_on local Where the command runs. local: on the Watcher machine. host: on the monitored host over SSH, see Checks over SSH.
copy false With run_on = "host": upload the script to the host before running it.
passive false true: Watcher runs nothing and waits for results sent over the API. See Passive checks.
format auto How the output is read: auto, nagios, key_value or json. See Output formats.
vars Values for the $name$ macros in the command, or the settings of a built-in check. Win over all other vars.
thresholds.<metric> Limits for a metric: { warn = "...", crit = "..." }. See Thresholds.
interval 1m Time between two checks.
retry_interval interval, at most 1m Time between checks while a problem is not yet confirmed (SOFT).
max_attempts 3, passive 1 How many problem results in a row confirm a problem (HARD). Only HARD problems notify.
timeout 60s After this time the command is killed and the result is UNKNOWN.
freshness Passive services only: the state becomes UNKNOWN when no result arrived for this long.
flap_detection true Detect services that change state too often. See Flap detection.
flap_low 5 Flapping ends when the state change rate drops below this percentage.
flap_high 20 Flapping starts when the state change rate reaches this percentage.
graphs true false: no graphs for this service's metrics.

Every value set here wins over the service's and the check's. All other values still come from them.

Changing a service on one host

[[host]]
name = "db01"
groups = ["linux"]
  [host.service.load]
  thresholds.load1 = { warn = "> 16" }

Removing a service from one host

The host group linux gives every member load, but db01 shouldn't have it:

[[host]]
name = "db01"
groups = ["linux"]
  [host.service.load]
  enabled = false

Adding a defined service with other values

[[host]]
name = "web01"
  [host.service.disk_root]
  vars.warn = "30%"

A service only this host has

[[host]]
name = "backup01"
  [host.service.backup_age]
  command = "/opt/scripts/backup_age.sh"
  interval = "1h"

for_each services

With for_each, [host.service.disk_data] changes only the service for the entry data, and [host.service.disk] changes all disk_* services of the host.

[[host]]
name = "db01"
vars.disks.root = { path = "/" }
vars.disks.data = { path = "/srv" }
  [host.service.disk]
  interval = "10m"          # disk_root and disk_data
  [host.service.disk_data]
  enabled = false           # only disk_data

Several host services

Each one starts with its own line:

[[host]]
name = "web01"
groups = ["linux"]
  [host.service.disk_root]
  vars.warn = "30%"
  [host.service.load]
  enabled = false
  [host.service.uptime]
  command = "uptime"

Host state

A host is UP or DOWN. The state comes from its host check: a service or a check that runs for the host itself.

State of the host check Host state
OK, WARNING UP
CRITICAL, UNKNOWN DOWN

Which one is the host check:

  1. host_check on the host, if set.
  2. Otherwise host_check from its host groups.
  3. Otherwise, if the host has an address: ping, your [service.ping] or [check.ping] if there is one, else the built-in ping check.
  4. Otherwise there is no host check, and the host is always UP.

host_check = false turns the host check off, also the automatic ping.

What the host state changes:

  • While a host is HARD DOWN, its other services don't send notifications. You get one notification for the host instead of one per service.
  • The host check notifies as the host: "web01 is DOWN", not "web01/ping is CRITICAL".
  • Retries count only CRITICAL and UNKNOWN results. A WARNING result means the host is UP and ends the retries.
  • A WARNING of the host check doesn't notify, because the host is still UP.

host_check takes the name of a service, for example [service.check_ping] with settings of its own, or of a check, also a built-in check like tcp. It isn't the plugin's name: check_ping works only if you named a service or check like that.

The host check is not one of the host's services. The web UI shows it with the host's state on the host page, not in the lists of services, and service totals don't count it. Notify rules and dependencies treat its alerts as alerts about the host. If the host also lists the same service in services, it runs once, as the host check. Settings for it on one host go in [host.service.<name>], as for a service.

ssh

The login for checks over SSH, used by checks with run_on = "host". Watcher connects to the host's address.

Field Default Description
user Required. User to log in as.
secret Required. Name of a key or password stored in Watcher. See Secrets.
port 22 SSH port.

The login is usually set once on a host group. A host can set some fields itself and take the rest from its host groups:

[hostgroup.linux]
members = ["web*", "db*"]
ssh = { user = "monitor", secret = "monitor" }

[[host]]
name = "db07"
groups = ["linux"]
ssh = { port = 2222 }          # user and secret from linux

proxmox

Settings for the Proxmox VE checks. A host is either a Proxmox VE server, with the API login, or a VM or container on one, which names that server.

Field Default Description
secret Proxmox VE server: name of the API token stored in Watcher. See Store the token.
fingerprint The SHA-256 fingerprint of the API's certificate, as Proxmox VE shows it (18:B4:0D:…). Only this certificate is accepted then, also a self-signed one.
port 8006 The API's port.
verify true Without fingerprint: the certificate must be trusted by the system and valid for the address. false accepts any certificate.
discover false Look for its VMs and containers every 10 minutes and offer them as hosts under Configuration → Discovery. See Accept VMs and containers.
host VM or container: the Proxmox VE host it runs on. Its checks ask that host's API, with its login.
vmid VM or container: its ID in Proxmox VE, e.g. 100. Needed with host.

A Proxmox VE server needs secret, from itself or a host group. A VM or container has only host and vmid; hosts that discovery adds get them written for them.

[[host]]
name = "pve1"
address = "192.0.2.10"
proxmox = { secret = "pve", fingerprint = "18:B4:0D:EC:C4:69:B9:5C:8B:30:C2:82:ED:4A:0C:B9:49:01:0A:3B:04:0F:55:86:68:A8:85:40:6F:22:F3:A2", discover = true }
services = ["proxmox-node", "proxmox-storage"]

[[host]]
name = "db01"
address = "192.0.2.21"
proxmox = { host = "pve1", vmid = 101 }
services = ["proxmox-guest"]
