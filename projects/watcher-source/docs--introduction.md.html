Introduction

Watcher monitors infrastructure: hosts, services, metrics and alerts. It is one binary with a built-in web UI. You configure it with TOML files or in the web UI, and it stores results in PostgreSQL. Nagios plugins and any script that prints a result work as checks.

Concepts

Term Meaning
check What to run: a command, its default values, thresholds.
service A check with its settings, put on hosts. On a host, a service has the ID host/service.
host A machine or device to monitor.
host group Hosts that get the same services and settings.
service group Services that are assigned or viewed together.
host check The service or check that decides whether a host is UP or DOWN. It runs for the host itself and shows on the host's page, not among its services.
contact Someone who receives notifications: by email, webhook, Slack, Teams, Telegram, ntfy, Gotify, PagerDuty, Jira or a script.
contact group A set of contacts.
notify rule Which contacts get which notifications.
dependency Holds notifications back while another host or service has a problem, like the router in front of them.
downtime group Hosts with recurring downtime windows.
time period When notify rules apply, for example business hours.
sink A second database that receives a copy of all results.
hub A Watcher that nodes at other sites connect to (role = "hub").
node A Watcher at another site, for example a customer's network, that connects to a hub.

States

Services Hosts
OK, WARNING, CRITICAL, UNKNOWN, and PENDING before the first result UP, DOWN

A new problem is first SOFT. It becomes HARD once it was seen max_attempts times in a row. Only HARD changes send notifications, so a single bad result doesn't wake anyone up. See SOFT and HARD states.

What works today

Single server:

  • Checks: Nagios plugins; scripts with Nagios, key=value or JSON output; passive results over the API; thresholds with units; built-in ping, TCP, HTTP, DNS and TLS certificate checks.
  • Proxmox VE: built-in checks for the cluster, nodes, storages, VMs and containers, backups and updates, through the API with a token stored encrypted; VMs and containers found on their own and added as hosts with one click.
  • Checks over SSH: run on the hosts without an agent; keys or passwords stored encrypted; pinned host keys; scripts copied to the hosts.
  • State handling: SOFT/HARD, retries, host UP/DOWN, flap detection, freshness of passive results.
  • Configuration: files and web UI, services, groups, for_each, Config Tree, validation with file and line, reload on save, edit locks between the web UI, watcher config edit and editors on the server.
  • Web UI: Tactical Overview, hosts, services, problems, groups, alert history, graphs, configuration forms and file editor.
  • Operations: acknowledgements, one-off and recurring downtimes, muted notifications, disabled checks, re-check, process info, scheduling queue.
  • Notifications: email, webhooks, Slack, Microsoft Teams, Telegram, ntfy, Gotify, PagerDuty, Jira tickets and scripts; reminders for open problems, escalations, time periods (business hours, on-call at night), dependencies (one alert about the router, not fifty about the hosts behind it), a log of every notification sent.
  • Storage: PostgreSQL or TimescaleDB, SQL views, read-only database login, copies to another PostgreSQL (sinks).
  • Access: users, sessions, two-factor authentication (TOTP), API tokens, HTTPS (also with certificates from Let's Encrypt or another ACME CA); the full API, everything the web UI does.

Nodes, first part:

  • Hub and nodes: nodes join a hub with a one-time token and stay connected over mutual TLS, dialing out from their site; the Nodes page shows which are connected. Nodes don't run checks yet.
